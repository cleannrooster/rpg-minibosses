# Anarchy RPG 3.0 — Scope

Status: **draft for review** (2026-10-14). Written in abstraction-only mode: it contains declarations, contracts and
state machines, not implementations.

3.0 has two jobs. It moves the namespace from `rpg-minibosses` to `anarchy_rpg`, and it makes adventurer NPCs the
center of the mod. The core idea is that **an NPC that isn't outright hostile can be spoken to.** Conversation is the
entry point to everything else: exchange, rumors, recruitment, and companion orders.

## M0 — Namespace migration

### Decided (2026-10-14)
1. **Everything is renamed.** That covers:
   - `content_namespace`, `fabric_mod_id` and `neoforge_mod_id` all become `anarchy_rpg`. They stay as three separate
     properties in `gradle.properties`, since the reason they're separate (identity, not spelling) still applies.
     Update the comment there: it was written because NeoForge rejects hyphens, and that's no longer the issue.
   - The Java package becomes `com.cleannrooster.anarchy_rpg`.
   - `archives_name` becomes `anarchy_rpg`.
2. **Existing worlds break.** No alias layer and no remapper. The changelog has to say plainly that 2.x worlds lose all
   mod entities, items, blocks, the guild hall dimension, and the infamy/benevolence stats.

### What the rename touches
- Asset and data folders.
- Every `Identifier.of(CONTENT_NAMESPACE, …)` call.
- Lang keys (`entity.rpg-minibosses.*` → `entity.anarchy_rpg.*`).
- Mixin config filenames and their `package` fields.
- Refmap names.
- `fabric.mod.json` and `neoforge.mods.toml`.
- The access widener filename.
- Spell Engine spell and assignment IDs.
- Template pools and structure sets.
- The config filename.
- Datagen output under `fabric/.../data`.

Don't start M1 until the rename has landed, so that no new ID gets created in the old namespace.

### Done when
A search of `common/`, `fabric/` and `neoforge/` (sources and resources) for `rpg-minibosses` and `rpg_minibosses`
finds nothing outside the changelog. Both loaders boot into a fresh world, the guild hall works, and an encounter
spawns.

## M1 — Factions, Standing, Disposition

### Decided (2026-10-14): three factions, generated per seed
Every world has exactly **three** factions. Each faction's **name** is drawn from a pool, and each gets a **flag**, with
the three flags in distinct colors (for example red, blue and green). Both the names and the colors are determined by
the world seed.

### Abstractions
```java
enum FactionSlot { FIRST, SECOND, THIRD }       // there are always exactly three; the slot is the stable identity

record FactionFlag(DyeColor base, List<BannerPatternsComponent.Layer> layers) {}   // rendered as a banner

record Faction(FactionSlot slot, Text name, FactionFlag flag) {}

// Data-driven pools: data/anarchy_rpg/faction_pool/names.json, .../flag_colors.json, .../flag_patterns.json
interface FactionPools {
    List<Text> names();
    List<DyeColor> colors();        // must contain at least three entries
    List<RegistryKey<BannerPattern>> patterns();
}

// World-level PersistentState (overworld).
interface FactionRoster {
    Faction get(FactionSlot slot);
    List<Faction> all();
    static FactionRoster generate(long worldSeed, FactionPools pools);
}

enum FactionRelation { ALLIED, NEUTRAL, RIVAL, AT_WAR }
interface FactionRelations {                    // symmetric; a faction is always ALLIED with itself
    FactionRelation between(FactionSlot a, FactionSlot b);
}

enum Disposition { HOSTILE, WARY, NEUTRAL, FRIENDLY, DEVOTED }
// Only HOSTILE refuses conversation. WARY can talk but cannot be hired, and exchange costs more.

record StandingThresholds(int hostileBelow, int waryBelow, int friendlyAbove, int devotedAbove) {}

// Server-only, world-level persistent state keyed by player UUID.
interface StandingLedger {
    int get(UUID player, FactionSlot faction);
    void apply(UUID player, StandingEvent event);   // the only way to mutate Standing
}

record StandingEvent(FactionSlot faction, StandingCause cause, int delta, @Nullable UUID npc) {}
enum StandingCause { KILLED_MEMBER, SPARED_MEMBER, PROVOKED, TRADED, HIRED, CONTRACT_DONE, CONTRACT_FAILED,
                     COMPANION_SERVED }

interface DispositionResolver {
    Disposition resolve(AdventurerNpc npc, ServerPlayerEntity player);
}
```

### Generation rules
- `generate` is a pure function of `(worldSeed, pools)`. It draws three **distinct** names and three **distinct**
  colors. Patterns may repeat, since color is what tells the factions apart.
- The result is **persisted** the first time it's generated, and loaded from the save from then on. That keeps names
  and flags stable even if a datapack or an update changes the pools later. The seed only decides the *first* roll.
- Faction names in the pool are translation keys, so they can be localized.
- The flag appears as a banner at camps and guild structures, and as a color tint in the conversation header. A
  recruited companion keeps its faction.

### Data flow
- `onDeath` and `setAngryAt` currently increment `INFAMY`. In 3.0 they emit `StandingEvent`s against the NPC's
  faction. `FactionRelations` then **propagate** a scaled share of the delta to the other two factions.
- NPC-versus-NPC targeting (`isEnemyOf`, and the `betrayal` target goal) also checks
  `FactionRelations.between(...) == AT_WAR`, alongside the current "we're already fighting" rule.
- The player-targeting predicate at `MinibossEntity.java:1070` becomes `resolve(npc, player) == HOSTILE`.
- `trueAnarchy` forces HOSTILE. `betrayal` and `despotism` keep their current meaning. The resolver applies these flags
  **before** it looks at Standing (see feedback_preserve_existing_rules: reproduce the existing rules, don't invent
  stricter ones).
- A provoked NPC (`angryAt == player`) resolves to HOSTILE for the duration of its anger timer, whatever the player's
  Standing is.

### Invariants
- There are always exactly three factions, each with a different color. No code path assumes a fourth.
- Disposition is **per (NPC, player) pair**. The same NPC can be hostile to one player and friendly to another, so the
  targeting code has to evaluate it per candidate player.
- Owned companions skip the resolver entirely. Their owner is always DEVOTED.
- Standing is clamped to a configured range. `INFAMY` and `BENEVOLENCE` are removed with no migration, since 2.x
  worlds break anyway (M0).
- Standing lives in world `PersistentState`, not loader-specific player attachments. That keeps it common-only code,
  works for offline players, and lets Rumors (M5) query it.

### Decided (2026-10-14)
- **Relations are rolled from the seed.** `FactionRelations` is generated together with the roster and persisted
  alongside it, so the three pairs (FIRST–SECOND, FIRST–THIRD, SECOND–THIRD) are fixed for the life of the world.
- **Factions are assigned per party.** Every NPC belongs to a party, and the party carries the faction. A camp's
  residents form one party, so each camp flies one flag. A patrol is one party. A lone wanderer is a party of one.

### Minimal party identity (pulled forward from M6)
Faction-per-party means 3.0 needs a party identity even though the parties rework (M6) moves to 3.1. This is only an
identity and a faction. There are no party templates or intents yet.
```java
record PartyId(UUID value) {}
record PartyMembership(PartyId party, FactionSlot faction) {}   // persisted on each NPC
interface PartyRegistry {                                        // world PersistentState
    PartyId create(FactionSlot faction);
    FactionSlot factionOf(PartyId party);
}
```
- `Patrol.spawnRPG` creates one party per spawned patrol and rolls its faction.
- Camp and tower residents share their anchor's party (see Turnover in M3).

### Invariants for rolled relations
- The relation table is symmetric, and a faction is always ALLIED with itself.
- **The roll is constrained so that never all three pairs are AT_WAR** (decided 2026-10-14). The three pairs are
  drawn with weights from the faction pool data. A draw that breaks the constraint is re-drawn deterministically from
  the same seed stream, so a given seed always lands on the same table.
```java
interface RelationRoll {
    FactionRelations roll(long worldSeed, RelationWeights weights);   // postcondition: at least one pair is not AT_WAR
}
```

### Terminology (2026-10-14)
Players and server owners see factions as **guilds**: in config comments, command output
(`/rpgminibosses guilds`, with `factions` kept as an alias) and log messages. The guild names already read as
guilds. The code keeps the `Faction*` names, and lang keys stay `faction.anarchy_rpg.name.*` (never shown).

### Implementation notes (M1, built 2026-10-14)
- The code is in `com.cleannrooster.anarchy_rpg.faction`. `Factions` is the entry point (`disposition`,
  `atWar`, `recordDeed`).
- **No `PartyRegistry`.** Each NPC stores its `PartyMembership` (party id plus faction) in its own NBT, under
  `Party`. Party members are always created with one shared faction and parties never change faction, so a
  registry would only duplicate that. M3's hub anchors can store a membership the same way.
- **Party adoption.** An NPC that has no party when it's first asked joins the party of the nearest untamed
  NPC within 24 blocks, or starts its own party if there's none nearby. This keeps camp residents (still
  spawned one at a time until M3) under one flag instead of brawling. Patrols create one party per patrol
  explicitly.
- **Standing numbers** keep the old hostility rule. A kill is −20 and a provoke is −4, and HOSTILE starts
  below −20, so "one kill, then one provoke" turns a faction hostile, exactly like the old `infamy > 5`.
  The other thresholds are WARY < −5, FRIENDLY > 20 and DEVOTED > 50. Standing is clamped to ±100, and a
  spare is +8. All of these are server config values.
- **Propagation:** ALLIED ×0.5, NEUTRAL ×0, RIVAL ×−0.25, AT_WAR ×−0.5.
- **War kills are real deaths (2026-10-14):** an adventurer killed by an adventurer of a faction at war with
  its own dies outright, with normal drops, instead of being downed and recruitable. Kills by players or
  companions (factionless, never at war) still down it.
- **Faction warfare:** untamed NPCs target untamed, non-downed NPCs whose faction is AT_WAR with theirs.
  This is behind `factionWarfare` (default on) and is skipped when `betrayal` is on.
- `INFAMY` and `BENEVOLENCE` are removed.
- The Magus Prime isn't a `MinibossEntity`, so it has no faction yet.
- **Debug commands:** `/rpgminibosses factions` lists the roster, the relations and your standing.
  `/rpgminibosses factions look` shows the party, faction and disposition of the NPC under your crosshair.
  `/rpgminibosses factions standing <first|second|third> <value>` sets your standing.

### Standing is shown in dialogue
Decided 2026-10-14: the player sees their Standing **only in the conversation screen**. The header shows the NPC's
faction flag and name, and your current Disposition tier with that faction (HOSTILE never reaches dialogue). Raw
numbers stay hidden. There's no HUD element and no standalone reputation screen in 3.0.
```java
record StandingView(FactionSlot faction, Disposition tier) {}   // sent inside OpenConversationPayload
```

## M2 — Conversation shell

### Abstractions
```java
enum ConversationOption { EXCHANGE, RUMORS, COMPANION_GEAR, GO_TO_BASE, STAY, FOLLOW,
                          SET_RENDEZVOUS_HERE, HIRE, DISMISS }

interface ConversationOptionRule {
    boolean available(AdventurerNpc npc, ServerPlayerEntity player, Disposition d);
    @Nullable Text unavailableReason(AdventurerNpc npc, ServerPlayerEntity player, Disposition d);
}

// S2C: open the dialogue. C2S: the option the player picked.
record OpenConversationPayload(int npcEntityId, Text greeting, StandingView standing,
                               @Nullable Text heardAboutYou, List<OptionEntry> options) {}   // heardAboutYou: see M5
record OptionEntry(ConversationOption option, boolean enabled, @Nullable Text reason) {}
record ChooseOptionPayload(int npcEntityId, ConversationOption option, @Nullable StayDuration stay) {}
```

### Flow
`interactMob` (main hand, not petrified, not in the guild hall's look-only rules) → resolve Disposition → HOSTILE: pass
(no conversation) → otherwise the server builds the option list → sends `OpenConversationPayload` → the client shows the
dialogue screen → `ChooseOptionPayload` → the **server re-validates** the option against current state before acting.

### Invariants
- The client never decides availability. The server always re-checks distance, liveness and Disposition when it
  receives `ChooseOptionPayload`.
- While a conversation is open the NPC stops wandering and faces the player, the same way `Merchant.customer` works
  today. Only one player can converse with an NPC at a time.
- Taking damage from that player closes the conversation and invalidates it.

### Implementation notes (M2, built 2026-10-14)
- The code is in `conversation/` (server, plus payloads under `conversation/net/`) and
  `client/conversation/` (the screen).
- Options are registered with a rule and a handler in `ConversationOptions`. An option with nothing
  registered never shows. Later milestones plug in Exchange, Hire, Rumors and the companion orders.
- The screen is vanilla-styled: the `popup/background` nine-slice panel, container text color
  `0x404040` with no shadow, and stock buttons. The faction name is drawn in its flag color, darkened if pale.
- M2 registers only **Follow** and **Stay** for your own companion. They replace the old right-click sit
  toggle and keep its replies. Stay is still untimed until M4. Every other conversation offers only
  Goodbye.
- Spawn eggs and name tags keep their vanilla use on adventurers. Right-clicking a downed adventurer
  still spares it.
- Conversations are server-side only and not saved, so a reload ends them.
- **Greetings (open decision, default chosen):** a fixed set of three lang lines per disposition,
  `conversation.anarchy_rpg.greeting.<tier>.<1-3>`. It could later vary by faction or archetype.

## M3 — Exchange

Three panes:
- **Left:** NPC stock. Randomly generated, and more than the NPC drops on death.
- **Middle:** your request.
- **Right:** your offer.

The more you put in the middle, the higher the price of everything in it. You can take the whole middle only if
`offerValue ≥ requestCost`.

### Abstractions
```java
interface ItemValuator {                       // pluggable; data-driven table first, heuristics as fallback
    double baseValue(ItemStack stack);
}
// Value sources in priority order: data/anarchy_rpg/item_value/*.json (exact item or tag) → rarity →
// enchantments → attribute modifiers (damage, armor, Spell Power if loaded) → durability fraction.

interface MarkupCurve {
    double multiplier(int requestedStackCount, double requestedBaseTotal);  // monotonic non-decreasing, ≥ 1
}

record ExchangeQuote(double requestCost, double offerValue, boolean acceptable) {}

interface ExchangePricing {
    ExchangeQuote quote(List<ItemStack> request, List<ItemStack> offer, Disposition d);
}
// requestCost = Σ baseValue(request_i) × markup(request) × dispositionFactor(d)
// offerValue  = Σ baseValue(offer_i)   × offerFactor(d)
// All values are in currency units: one currency item = 1.0.

// Config: currencyItem (replaces tradeItem; default "minecraft:emerald").
interface Currency {
    Item item();
    boolean isCurrency(ItemStack stack);   // currency is always valued at exactly 1.0 per item and is never marked up
}

interface NpcStock {
    List<ItemStack> view();
    boolean isGenerated();
    void generate(ServerWorld world, AdventurerNpc npc, long seed);  // lazy: runs once on first open, then persisted to NBT
    // There is deliberately no restock() method.
}

class ExchangeScreenHandler extends ScreenHandler { /* three slot groups: STOCK, REQUEST, OFFER, plus the player inventory */ }
```

### Decided (2026-10-14)
- **Equipped gear is not for sale.** STOCK never contains what the NPC is wearing or holding, so a purchase can never
  change how the NPC fights. Death drops are the equipped gear, as they are today with drop chance 100.
- **Stock never refills.** A given NPC's pack only ever shrinks. Fresh stock comes from fresh NPCs (see Turnover
  below).
- **Offered items are destroyed** when a trade confirms. Exchange is a pure item sink, so sell-back loops are
  impossible by construction and `offerFactor` only needs to express Disposition, not anti-exploit margins.
- **The currency is configurable**, defaulting to emeralds.

### Turnover: camps become hubs
Decided 2026-10-14: there is **no guild hall in 3.0.** Camps (`plains_camp`, `desert_camp`, `snowy_camp`) and
repurposed towers (`repurposed_pillager_outpost`) become **hubs**, not farming grounds. Turnover simulates
adventurers coming and going, which keeps stock fresh, since a given NPC's stock never refills.
```java
enum HubKind { CAMP, TOWER }            // towers behave like camps; the kind only changes layout and resident count

// One per placed camp or tower, keyed by structure start. Stored in world PersistentState.
record HubAnchor(BlockBox bounds, BlockPos center, HubKind kind, PartyId residentParty) {}

interface AdventurerTurnover {
    void onAnchorLoaded(ServerWorld world, HubAnchor anchor, long worldTime);  // world-time based, so it catches up on load
}
record TurnoverState(long lastRotationWorldTime, int targetResidents, List<UUID> residents) {}
```

**Changes to the structure data (this is M3 work):**
- Remove every trial spawner from the camp templates. Seven templates contain them: `camp/desert`, `desert3`,
  `pit`, `pristine`, `pristine3`, `snow` and `snowy_2`, 13 spawner blocks in total.
- Remove the `spawn_overrides` from the camp structures (`plains_camp`, `desert_camp`, `snowy_camp`) and from
  `repurposed_pillager_outpost` (decided 2026-10-14). They respawn adventurers indefinitely inside the bounding box,
  which is exactly the farming loop. Turnover becomes the *only* source of residents. That includes a hub's first 8
  residents, which are placed when the anchor is created.
- `CANTHIRE` is currently set for `SpawnReason.TRIAL_SPAWNER`. With no trial spawners, camp residents become hireable
  by default.
- Each hub gets a banner in its party's faction colors.
- If you're editing templates in-game, back up the `.nbt` files first (see feedback_generator_clobbering).

**Turnover rules:**
- A hub's resident party, and so its faction, is fixed when the hub is generated. Replacements join that same party,
  so a camp never changes flag.
- Rotation retires some residents. A retired resident walks out of the structure if it's being watched, and despawns
  if not. Replacements arrive with new stock seeds. Recruited companions and NPCs that are mid-conversation are never
  retired.
- Rotation runs on world time, evaluated when the anchor's chunk loads. It is never a ticking scan.
- NPCs in the wilderness (patrols, wanderers) have no turnover. Their stock is simply whatever they rolled.
- Killing a resident doesn't refill the hub. Only rotation brings a replacement, so a hub can be emptied for a while
  but can't be farmed.

### State machine
`CLOSED → OPEN(customer)`. Inside `OPEN`, the player moves items STOCK⇄REQUEST and inventory⇄OFFER, and every move
re-quotes. Then:
- `CONFIRM`: if `acceptable`, an **atomic swap**. REQUEST goes to the player and OFFER is destroyed. Then back to OPEN.
- `CLOSE`: REQUEST returns to STOCK and OFFER returns to the player. Then CLOSED.

### Invariants
- REQUEST items are always still owned by the NPC. Crashes, disconnects and the NPC dying all resolve as `CLOSE`, and
  no item is ever lost or duplicated.
- Quotes are computed only on the server. The client sees a mirrored quote for display.
- `MarkupCurve` is monotonic. Adding an item to REQUEST can never lower the per-item price of what's already there.
- Stock generation is deterministic from a stored seed, and stock never includes equipment.

### Implementation notes (M3 Exchange, built 2026-10-14)
- The code is in `exchange/` (server) and `client/exchange/` (screen).
- **Stock** (`ExchangeStock`, 9 slots) is generated the first time the Exchange option is checked, and saved
  under the adventurer's `ExchangeStock` NBT. It fills in priority order until all 9 slots are used:
  - **Boss key:** an `exchangeBossKeyChance` (8%) chance of one item from the `anarchy_rpg:boss_keys` tag
    (Lavos Horn, Gemini Fragment, Deatomized Fragment). These are priced at 48, 64 and 96 in
    `item_values.json`.
  - **Drop pool:** `exchangeStockDropRolls` (4) rolls of the adventurer's own loot table as loaded, so the
    Spell Engine compat drops and the RPG Series loot-tier injection are included. The rolls treat the
    asking player as the killer, and boss keys are filtered out of them.
  - **Dungeon loot:** an `exchangeDungeonLootChance` (30%) chance of one roll of a random chest table from
    `exchangeDungeonLootTables` (simple dungeon, mineshaft, desert pyramid, jungle temple). At most
    `exchangeDungeonLootMaxStacks` (3) random stacks of it are kept.
  - **Weapons:** `exchangeStockWeapons` (3) picks from the weapon pool.
  - **Supplies:** `exchangeStockSupplyRolls` (3) rolls of `loot_table/exchange/supplies`.
  - **Ender Dragon table:** one roll.
- **Values** come from `data/anarchy_rpg/item_values.json` (exact items, then tags). Anything else is priced
  by heuristics: rarity floor (0.1 for stackable commons, 1 for other commons, 3, 8, 20), plus attribute
  modifiers (armor ×1.5, toughness ×2, attack speed ignored), plus 1.5 per enchantment level, times
  durability left.
- **Pricing:** `exchangeMarkupPerStack` 0.15, `exchangeAngryPriceMultiplier` 2.0 and
  `exchangeDevotedPriceMultiplier` 0.75. These are linear in standing: 2.0 at the hostile threshold, 1.0 at
  0, 0.75 at the devoted threshold. An owner always gets the devoted price. Each trade gives
  `standingTrade` +1.
- **Config:** `tradeItem` is renamed `currencyItem` (default emerald). It is still the guild hall's trade
  item too.
- **Screen:** the vanilla dispenser panel, nine-sliced, with the `container/slot` sprites and the
  `villager/trade_arrow` sprite. Text is 0x404040 with no shadow.

### Implementation notes (M3 hubs, built 2026-10-14)
- The code is in `hub/`. `HubTurnover` does discovery, setup and rotation. `HubState` saves each world's
  hubs, keyed by structure-start chunk.
- **Which structures are hubs** is set by the structure tags `anarchy_rpg:hub_camps` (plains, desert and
  snowy camps) and `anarchy_rpg:hub_towers` (repurposed outpost), so datapacks can add more.
- **Discovery:** every 100 ticks, loaded chunks within `hubScanRadiusChunks` (8) of each player are checked
  for hub structure starts. A hub is handled once per stretch of being loaded, 100 ticks after it loads,
  which gives its residents' entities time to load.
- **First setup:** the hub gets a new party (and so a faction), `hubResidents` (8) residents placed on
  standable ground inside it, and a standing banner in its flag colors near the center. Columns are
  scanned bottom-up, so residents land on the ground floor rather than tower roofs. Setup never waits
  for watchers.
- **Rotation:** for each whole `hubRotationTicks` (72000) interval that has passed, `hubRetireCount` (4) of
  the longest-staying residents are retired (up to all of them), then the hub refills to 8. It is skipped
  while a player is within `hubWatchRadius` (48) blocks; residents mid-conversation or mid-trade stay. Dead
  or recruited residents are pruned at rotation, so only rotation fills their places.
- **Retired residents despawn.** Since rotation only happens unobserved, nobody needs to see them walk off.
- **Data changes:**
  - Trial spawners were swapped for air in all 7 camp templates.
  - `spawn_overrides` were removed from the camps and the outpost.
  - The `pit` and `guild_hall` structure sets are switched off with `frequency: 0` (the pit's method is
    changed to `default`, where 0 means never). Their files stay.
- **Debug:** `/rpgminibosses hubs` reports the nearest hub. `/rpgminibosses hubs rotate` forces a rotation.

### Decided (2026-10-14, round 3)
- **`pit` is deprecated.** It stops generating in 3.0: `worldgen/structure_set/pit.json` comes out of generation.
  The structure, pool and template files stay in place, marked deprecated, until they're deleted in 3.1. It is not a
  hub.
- **The old merchant trading is removed (2026-10-14):** adventurers no longer implement vanilla's
  `Merchant`. That removes the emerald offers, the trade screen, the `Offers` NBT, and the `tradeAmount`,
  `tradeMultiplier` and `rareTradeMultiplier` config. Exchange replaces it. The "customer" that holds an
  adventurer still for its windows is now the mod's own field.
- **The guild hall is deprecated (2026-10-14):**
  - Its dimension ships as `dimension/guild_hall.json.deprecated`, so it doesn't load.
  - Its block, interaction and respawn hooks and the `/guildHideout` and `/leaveGuildHideout` commands are
    no longer registered. They're kept in `RPGMinibosses.registerGuildHall()`, marked `@Deprecated`, for 3.1.
- **The guild hall is switched off for now.**
  - The dimension and `/guildHideout` stay behind the existing `guild = false` config.
  - The overworld `guild_hall` structure also stops generating. Its structure set
    (`worldgen/structure_set/guild_hall.json`) is generating today, and the config flag doesn't touch it.
  - Nothing is deleted; M7 (3.1) revives it.
- **Hub size and rotation:** camps and towers each hold **8 residents** (`targetResidents = 8`), with a rotation every
  **3 Minecraft days** (72 000 ticks, about one real hour). Both values are configurable.
  - My view: the interval is right. It's long enough that a hub feels inhabited, and short enough that you'll see
    new stock across a few play sessions.
  - **Rotation is staggered** (decided): each rotation retires the **4** longest-staying residents. Every visit
    shows fresh stock, but a hub never turns into a crowd of strangers overnight, and a resident stays for about two
    cycles. The retire count is configurable (`turnoverRetireCount = 4`).
  - Catch-up: if a hub was unloaded for many intervals, apply `min(missedRotations × 4, 8)` replacements once. Don't
    replay each rotation.
  - Watchtowers have less floor space than camps. Make sure the 8 residents' spawn positions in the tower templates
    don't stack everyone on one platform.
- **Disposition pricing:** `dispositionFactor` is a continuous curve over Standing, not a per-tier step, so prices
  move smoothly as Standing changes.
```java
interface DispositionPricing {
    double factor(int standing, StandingThresholds t);   // monotonic non-increasing in standing; clamped to [floor, 2.0]
}
```
  - At the HOSTILE threshold (the angriest Standing that still allows dialogue) the factor is **2.0**. That's the
    cap: prices are never more than double.
  - At NEUTRAL it's **1.0**.
  - It eases down to a modest discount floor at DEVOTED (suggested 0.75, configurable).
- **Stock does not drop on death.** Only equipped gear drops.

## M4 — Companion (recruited mercenary)

### Abstractions
```java
enum CompanionMode { FOLLOWING, STAYING, TRAVELING_TO_BASE, AT_BASE, DOWNED }

record CompanionOrders(CompanionMode mode, long deadlineWorldTime,      // STAYING and DOWNED only
                       @Nullable GlobalPos stayPos) {}

enum StayDuration { SHORT, MEDIUM, LONG }   // config-defined lengths; there is deliberately no INFINITE

// The base, shown to the player as the "rendezvous point". It is stored per player, not per companion,
// so it survives a change of companion.
record CompanionBase(GlobalPos pos, BaseSource source) {}
enum BaseSource { PLAYER_SPAWN, RENDEZVOUS }
// PLAYER_SPAWN resolves at use time to the player's respawn point, falling back to world spawn.
// RENDEZVOUS is the player's exact position when they press "Set rendezvous point here."

// World PersistentState. Enforces one companion per player.
interface CompanionRegistry {
    Optional<CompanionRecord> companionOf(UUID owner);
    RecruitResult tryBind(UUID owner, AdventurerNpc npc, RecruitChannel channel);
    void release(UUID owner);
    CompanionBase baseOf(UUID owner);
    void setRendezvous(UUID owner, GlobalPos exactPlayerPos);
}
record CompanionRecord(UUID npcUuid, GlobalPos lastKnown, CompanionOrders orders,
                       @Nullable VirtualTrip trip, NbtCompound snapshot) {}
enum RecruitResult { BOUND, ALREADY_HAS_COMPANION, NPC_CANT_HIRE, NPC_UNWILLING, CANT_AFFORD }

// Recruitment: either defeat, or pay.
enum RecruitChannel { DEFEATED, HIRED }
interface HirePricing {
    double hirePrice(AdventurerNpc npc, int standingWithNpcFaction);   // in currency units; non-increasing as Standing rises
}

// Travel to base: walk while the companion is loaded and near enough; otherwise simulate the walk with a delay.
record VirtualTrip(GlobalPos destination, long departedAt, long arrivesAt) {}
interface BaseTravel {
    TravelPlan plan(AdventurerNpc npc, CompanionBase base);   // WALK or VIRTUAL
    long simulatedDuration(double remainingDistance);         // remainingDistance ÷ the configured walk speed
}
enum TravelPlan { WALK, VIRTUAL }

interface CompanionController {        // owned by the NPC; drives brain and goal gating from CompanionOrders
    void order(CompanionOrders orders);
    void onLethalDamage(DamageSource source);   // → DOWNED, never death
    void tickOrders(long worldTime);            // deadline checks
}
```

### State machine
```
           recruit
  (free) ──────────► FOLLOWING ◄──────────────────────┐
                        │   │  "Stay" (duration)       │ "Follow" (owner present)
         "Go to base"   │   └──────────► STAYING ──────┤
                        ▼                    │ deadline│
                TRAVELING_TO_BASE ◄──────────┘         │
                        │ arrived                      │
                        ▼                              │
                     AT_BASE ──── "Follow" ────────────┘
  any mode ── lethal damage ──► DOWNED ── deadline ──► the mode it was in before (STAYING → TRAVELING_TO_BASE if its deadline also passed)
```

### Invariants
- **One companion per player.** `tryBind` refuses when the player already has one; it never silently replaces. Dismissing
  frees the slot immediately.
- **Immortal.** Lethal damage moves the companion to DOWNED: invulnerable, not targetable, AI off, using the existing
  `DOWN` visuals. Damage that bypasses invulnerability (void, `/kill`) moves it to `AT_BASE` with full health, through
  the lost-companion restore path.
- **Deadlines use world time, not tick counters.** A companion in an unloaded chunk doesn't tick, so its deadlines are
  evaluated on load and on registry sweeps, against `deadlineWorldTime`.
- **Stay is never infinite.** No code path can produce `STAYING` without a finite deadline.
- The existing DOWN state ("downed, unowned, recruitable") and the companion's DOWNED state are different things.
  Don't reuse one flag for both meanings.

### Decided (2026-10-14)
**Travel to base:**
- `TRAVELING_TO_BASE` starts with `plan`. If the companion is loaded and within `walkRange` of the base, it is `WALK`:
  it pathfinds normally.
- Otherwise it is `VIRTUAL`: the registry stores a `VirtualTrip` with
  `arrivesAt = now + simulatedDuration(distance)`, and the entity is removed after its NBT is written into `snapshot`.
- If the companion's chunk unloads partway through a walk, it switches to `VIRTUAL`. The remaining distance is
  measured from its last known position.
- When `now ≥ arrivesAt` and the base chunk is loaded, the companion is re-created from `snapshot` at the base and
  enters `AT_BASE`. If the base chunk isn't loaded, the trip is held and resolved when that chunk next loads.

**Recruitment channels:**
- `DEFEATED`: the existing spare flow. The NPC is downed, unowned, and not `CANTHIRE`.
- `HIRED`: a dialogue option opens Exchange in hire mode. There is no STOCK or REQUEST pane, only OFFER against a
  fixed `hirePrice`. Price is driven by favor (Standing with the NPC's faction): higher Standing means cheaper.
- WARY NPCs still refuse to be hired, and HOSTILE NPCs can only be defeated. Hiring emits `StandingEvent(HIRED)`.

**Rendezvous point:**
- The dialogue option is **"Set rendezvous point here."** It stores the player's exact position at the moment they
  press the button.
- Until it's set, the base is the player's spawn point.
- It is per player, so it carries over to a future companion.
- **The rendezvous must be within 64 blocks of the player's spawn point**, in the same dimension. If it's farther,
  the option is shown disabled, with the reason.
- If the player's spawn point later moves so that a stored rendezvous is more than 64 blocks away, the rendezvous is
  dropped and the base falls back to the spawn point (decided 2026-10-14). The check runs whenever `baseOf` is read,
  so it doesn't need a hook into every way the spawn point can change. If the companion is `AT_BASE` at the dropped
  rendezvous at that moment, it moves to `TRAVELING_TO_BASE` toward the spawn point.

**Dismissal:**
- Dismissing frees the companion slot and returns the companion's gear to the owner, who is present because
  dismissal is a dialogue option. The NPC then *leaves*.
- Leaving uses the same `WALK` → `VIRTUAL` pattern as travel to base, with a destination far away from the owner. The
  NPC walks until its chunk unloads, then simulates the rest of the walk. When the trip ends, its record is deleted
  and it does not come back.
```java
enum TripPurpose { TO_BASE, DEPARTING }
record VirtualTrip(GlobalPos destination, long departedAt, long arrivesAt, TripPurpose purpose) {}
// This replaces the VirtualTrip above. A DEPARTING trip resolves by discarding the snapshot, not re-materializing it.
```

**Lost companions come back from the snapshot.**
- On registry sweep, owner login, or a base-chunk load, if the companion's entity can't be found where its record
  says it should be, it is re-created from `snapshot` at the base in `AT_BASE`.
- `snapshot` is refreshed whenever the companion's chunk saves, and whenever orders or gear change. That keeps a
  restored companion close to its latest state.
- Void and `/kill` damage go through the same path: the companion reappears at base with full health.
- Uniqueness check: before restoring, confirm that no live entity with `npcUuid` exists in any loaded world. That
  stops a slow-loading chunk from producing two copies.

### Implementation notes (M4a companion core, built 2026-10-14)
- The code is in `companion/`:
  - `Companions`: service, entity tick, sweep, restore
  - `CompanionRegistry`: overworld saved data holding companions, rendezvous points and last-known spawns
  - `CompanionRecord`
  - `CompanionOptions`: the conversation orders
- **Orders** (owner only):
  - Follow
  - Wait here: one option followed by a vanilla slider, 1–24 Minecraft hours (1000 ticks each, default 6).
    The client sends the hours with the option and the server clamps them.
  - Wait at rendezvous point (replaces "Go to base"): disabled with "Set a rendezvous point first" until
    one exists. Nothing sends a companion to the spawn point any more. A Wait that runs out with no
    rendezvous point sends the companion back to following its owner; with one, it walks or travels there.
  - Set rendezvous point here: disabled with a reason when you're farther than `companionRendezvousRadius`
    (64) from your spawn point
  - Dismiss
- **Immortal:** a lethal blow sets `COMPANION_DOWNED`, a tracked flag separate from the recruitable `DOWN`.
  The companion stays down for `companionDownedTicks` (1200), then gets up at `companionReviveHealth` (50%)
  in its previous mode, and its Stay timer keeps running. Every downed check (AI, animation, targeting,
  harm rules, conversation, Exchange) reads `isIncapacitated()`, which covers both flags. Damage that
  bypasses invulnerability kills the entity without drops, and the sweep re-creates it at base.
- **Travel:** within `companionWalkRange` (128) and in the same dimension, the companion walks. Otherwise it
  vanishes onto a simulated trip: distance divided by `companionTravelBlocksPerTick` (0.2), Nether ×8, and
  capped at `companionCrossDimensionMaxTicks` (48000) across dimensions. A companion whose chunk unloads
  mid-walk is picked up by the sweep as "unloaded while heading home" and continues as a trip from where
  it was last seen. There is no unload hook: `Entity.setRemoved` is final in 1.21.1.
- **One live copy:** `incarnation` goes up with every re-creation. A loaded copy whose number is behind
  removes itself, and nothing is re-created while an entity with the UUID is alive anywhere.
- **Lost companions:** if the companion is missing from its loaded chunk for 200 ticks, or was killed
  through immortality, it is restored from its snapshot at base, once the base chunk is loaded. The snapshot
  is refreshed every 200 ticks and on every order.
- **Dismiss** frees the slot and clears the owner. The ex-companion walks 64 blocks away and is removed
  once nobody is within 48 blocks (or after 2400 ticks). It does not come back.
  - Note: returning gear waits for M4c, since there's no player-given gear yet.
- **Factionless while devoted:** an owned companion answers to its player, not to a faction.
  `Factions.factionOf` returns null for it, so:
  - it shows no faction line in dialogue and no floating banner
  - it shows its owner's face (skin face plus hat layer, from the player list, falling back to the default
    skin) above it instead of a flag, with the same 16-block rule
  - it is never at war
  - deeds toward it change no standing
  - it is neutral to everyone but its owner, and Exchange prices it at standing 0

  Its party is kept, only set aside.
- **Storage instead of Exchange:** an owned companion has no Exchange option.
  - Its owner gets **Storage** instead: the companion's nine slots, moved freely in the vanilla dispenser
    layout and texture (`CompanionStorageScreenHandler`, menu `anarchy_rpg:companion_storage`).
  - Recruiting clears the trade stock (`clearForRecruit`), so storage starts empty and the trade goods
    can't be taken for free. It is never generated again.
  - Dismissing hands the storage back to the owner.
- **New spawn point:** when the sweep sees an owner's spawn point change and a rendezvous point exists, it
  moves the rendezvous point to the new spawn. A companion waiting there, loaded or not, then heads over,
  walking or on a simulated trip. With no rendezvous point, nothing moves.
- **Lost companions** (missing, or killed through immortality) reappear at the rendezvous point, or at the
  spawn point if there is none (`baseOf`). This is the only use of the spawn point, and never an order.
  Restores land on standable ground beside the target, not inside a bed.
- **Dialogue layout:** when the options would run past the screen height, they flow into up to three
  columns (150px buttons, as in vanilla's two-column menus), so every option is always visible.
- **Recruiting by defeat** goes through the registry. A second companion is refused with "You already have
  a companion."
- **Debug:** `/rpgminibosses companion`.

### Implementation notes (M4c equipment, built 2026-10-14)
- **Equipment option** (owner only) opens `CompanionEquipmentScreenHandler` (menu
  `anarchy_rpg:companion_equipment`). The layout follows vanilla's inventory screen: armor column, the
  companion drawn in vanilla's preview box (from `inventory.png`), main and off hand, and the player
  inventory. Empty slots show vanilla's armor, sword and shield icons. The panel is the shared
  `VanillaPanel` (tiled dispenser art), now used by Exchange too.
- **The slots are the companion's real equipment**, so vanilla applies every item's attribute modifiers on
  equip. Attributes the companion's type doesn't have do nothing.
- **Main hand** only takes items in `#anarchy_rpg:companion_weapons/<adventurer id>`:
  - mercenary: crossbows (its attack needs one)
  - juggernaut: axes, double axes, glaives, hammers
  - templar: swords, claymores, glaives
  - trickster: swords, daggers, sickles
  - archmage_fire: damage staves

  The RPG Series tags are optional entries.
- **Armor** goes only in its own slot. **Off hand** takes anything.
- **Armor never renders:** the adventurer renderer only draws the main-hand stack on `itemBone` and has no
  armor layer.
- **Bound gear:** gear the adventurer had when recruited is marked bound (custom data
  `anarchy_rpg:bound`). It can be replaced (and is then gone) but never taken out, hotbar-swapped or
  thrown, so recruiting isn't a way to loot an adventurer's weapon. Dismissing returns only the owner's
  gear; bound gear leaves with the companion.

### Implementation notes (M4b hiring, built 2026-10-14)
- **Hire option:** shown on any adventurer that isn't anyone's companion. It's disabled, with the reason,
  when the adventurer is marked not for hire (`CANTHIRE`, e.g. trial-spawner ones), when it's WARY of you,
  or when you already have a companion. HOSTILE adventurers won't talk, so they can only be defeated.
- **Price:** `companionHirePrice` (32) × the Exchange standing curve (×2 at the hostile threshold down to
  ×0.75 devoted), in currency units.
- **Hire window:** vanilla `dispenser.png` at native size (`HireScreenHandler`, menu `anarchy_rpg:hire`).
  Payment goes in the 3×3 grid, with the price and the offer's value left of it and **Hire** right of it.
- **On Hire,** the server re-checks every rule, then:
  - destroys the payment
  - records `standingHire` (+2) with the faction before recruiting, while the adventurer still has a
    faction
  - recruits through the registry, so the stock is cleared and gear is bound, exactly as with sparing

  Closing without hiring returns the offer.
- **Healing revives:** any `heal()` on a downed companion (healing potions, regeneration, healing spells)
  gets it straight back up in its previous mode, keeping its health plus the heal. It doesn't wait out
  the down timer or get the 50% revive.
- **Rest near spawn:** within `companionRestRadius` (64) of the owner's spawn point, same dimension, and
  out of combat (no target, not hit for 5 seconds), a companion regains `companionRestHealPerSecond` (1)
  health a second. Never while downed, since healing would stand it straight up.
- **Owner can't hurt their companion:** any damage whose attacker is the owner (melee, projectiles, TNT,
  spells) is refused. `/kill` and the void aren't from the owner, so they still go through the restore path.

### Implementation notes (companion failsafes, built 2026-10-14)
Nothing can leave a player locked out of companions:
- **Lost track of you:** a companion that is FOLLOWING or DOWNED while its owner is online, and has been
  away for `companionLostTimeoutTicks` (2400, 2 min), makes its way home as a simulated trip and tells the
  owner. "Away" means unloaded, in another dimension, or farther than `companionLostDistance` (256). The
  trip lands at the rendezvous point, else the spawn point. Time only counts while the owner is online, so
  logging off never sends a companion home.
- **Home without a rendezvous point** is the spawn point. A companion sent there waits (AT_BASE) and follows
  spawn moves. Orders still need a real rendezvous point: "Wait at rendezvous point" stays gated, and a Wait
  that runs out with none still returns to following.
- **A dimension that no longer exists:** a trip or restore aimed at it lands at the overworld spawn instead
  of never resolving.
- **Released copies never re-bind:** an owned entity with no record and `incarnation > 0` was released while
  unloaded, so it simply leaves. Only incarnation-0 (pre-registry) companions are adopted.
- **Player commands (no permission):**
  - `/companion recall`: sends it home now, loaded or not.
  - `/companion release`: frees the slot. A loaded companion is dismissed normally, with gear and storage
    returned. An unloaded one is released and its carried items are lost; the command says so.

### Cross-dimension trips
Decided 2026-10-14: **a cross-dimension trip takes at most 2 Minecraft days** (48 000 ticks). Within one dimension
the delay is distance ÷ walk speed, as before. A trip that crosses dimensions uses the same distance-based delay,
measured in overworld-equivalent distance, and is then clamped to 48 000 ticks.
```java
long simulatedDuration(double remainingDistance, boolean crossesDimension);   // replaces the one-argument form
```

## M5 — Rumors

### Abstractions
```java
enum RumorKind { STRUCTURE, BOSS, PLAYER }

record Rumor(RumorKind kind, Text subject, @Nullable RegistryKey<World> dimension,
             Direction8 bearing, DistanceBand distance, long issuedAt) {}
enum DistanceBand { NEAR, A_DAYS_WALK, FAR }        // deliberately fuzzy

interface RumorSource {
    RumorKind kind();
    Optional<Rumor> find(ServerWorld world, AdventurerNpc npc, ServerPlayerEntity asker, RumorMemory memory);
}

interface RumorCharges {               // persisted on the NPC
    int current(); int max();
    boolean spend();
    void accrue(double adventureProgress);
}

interface AdventureMeter {             // companions only: turns adventuring into charge progress
    void onOwnerTravel(double blocksOutsideBaseRadius);
    void onCombatAssist(LivingEntity killed);
    void onNewChunkVisited();
}

interface RumorMemory {                // per player (decided): shared across every NPC, in world PersistentState
    boolean alreadyTold(UUID player, RumorSubjectKey subject);
    void markTold(UUID player, RumorSubjectKey subject);
}
record RumorSubjectKey(RumorKind kind, String stableId) {}   // e.g. structure start pos, boss UUID, player UUID

// Accuracy is driven by the asker's Standing with the NPC's faction.
enum RumorAccuracy { PRECISE, MOSTLY, UNRELIABLE }
interface RumorAccuracyPolicy {
    RumorAccuracy accuracyFor(Disposition d);   // FRIENDLY/DEVOTED → PRECISE, NEUTRAL → MOSTLY, WARY → UNRELIABLE
    double truthChance(RumorAccuracy a);        // PRECISE 1.0, MOSTLY 0.8, UNRELIABLE 0.4
}
interface RumorDistorter {             // turns a true rumor into a plausible false one
    Rumor distort(Rumor truth, Random random);   // wrong bearing and/or wrong band, same real subject
}

// Lets a player learn, in-world, that someone has been asking about them.
interface AskedAboutLedger {           // world PersistentState, keyed by target player
    void record(UUID target, AskedAboutEntry entry);
    List<AskedAboutEntry> drainUndelivered(UUID target);
}
record AskedAboutEntry(UUID asker, Text askerName, FactionSlot askedNpcFaction,
                       Direction8 bearingFromTarget, long askedAt) {}

// Only players who take part in the NPC world can be the subject of a rumor.
interface RumorEligibility {            // world PersistentState: a set of player UUIDs
    boolean isRumorSubject(UUID player);
    void markEngaged(UUID player);      // set the first time the player opens a conversation with any NPC
}
```

### Sources
- **Structures:** the search is limited to the tag `#anarchy_rpg:rumorable` with a capped radius. `locateStructure` is
  expensive, so run it at most once per request and never on a tick.
- **Bosses:** a combination of
  - loaded `AdventurerNpc`s of BOSS rank,
  - encounter placements tracked by `MinibossEncounterSpawnManager`, and
  - optionally any entity in a `#anarchy_rpg:rumor_bosses` tag, which lets other mods' bosses count.
- **Players:** other online players who pass `RumorEligibility.isRumorSubject`, reported as a fine bearing and a
  tight distance band. A server config switch can turn PLAYER rumors off entirely.

### Decided (2026-10-14)
**Accuracy follows Standing:**
- Good Standing (FRIENDLY or DEVOTED) gets **precise** rumors: always true, with a 16-point bearing and a tight
  distance band.
- NEUTRAL gets rumors that are **80% correct**.
- Angry (WARY) gets rumors that are **40% correct**.
- An incorrect rumor is about a *real* subject, with a wrong bearing and/or distance. That way it's misleading but
  not fabricated. The player is never told whether a rumor is true.

**"Someone asked about you" is delivered in-world:**
- When a PLAYER rumor is told, the target gets an `AskedAboutEntry`. It's delivered through the `heardAboutYou`
  line the next time the target talks to *any* adventurer, as gossip. **Gossip names the asker** (decided
  2026-10-14). For example: "Steve was asking after you at a [red-flag] camp. Came from the east."
- Each entry is delivered once, then dropped.
- The NPC that gossips does not have to be the one that was asked.

**Memory is per player:**
- Once you've been told a subject truthfully, no NPC anywhere will tell you about it again.
- **Only true rumors mark a subject as told.** If false ones did, a player who got a wrong rumor could never learn
  the truth about that subject, which is the frustration this rule exists to prevent.

### Invariants
- One spent charge buys one rumor. If no source finds anything, **no charge is spent.** A false rumor still costs its
  charge.
- PRECISE means a 16-point bearing and a tight distance band, never coordinates (decided 2026-10-14).
- Accuracy is rolled on the server each time a rumor is told. Asking about a subject that came back false is a fresh
  roll that costs another charge, so charges are the limit on fishing for the truth.
- A non-companion NPC's charges don't regenerate (or regenerate slowly, by world time). A companion's regenerate
  through `AdventureMeter`. A companion's owner is DEVOTED, so companion rumors are always precise.
- **Players who don't take part in the NPC world are never rumor subjects** (decided 2026-10-14). A player becomes
  eligible the first time they open a conversation with any NPC, and the flag is permanent. Fighting NPCs doesn't
  count, so a player who only ever kills hostile adventurers stays hidden. That's my reading of "simply don't
  interact"; if fighting should count too, add `markEngaged` to the kill path.
- Eligibility is checked when the rumor is generated, so an ineligible player can't show up as a false rumor either.

  way M1–M5 depend on the interface, not on the 1,772-line class.

## Decided (2026-10-14)
- **Cut line:** 3.0 is M0–M5. M6 (parties rework) and M7 (Guild Hall hub, Contracts) are 3.1.
- **M0:** everything is renamed to `anarchy_rpg` (namespace, both mod IDs, Java package), and 2.x worlds break.
- **M1:**
  - Three factions per world. Names come from a pool, and each faction has a flag in its own distinct color.
  - The relations between them are rolled from the seed too. All of it is persisted.
  - Factions are assigned **per party**, which requires a minimal `PartyId`.
- **M3:**
  - Equipped gear is never for sale, and stock never drops on death.
  - Stock never refills; Turnover keeps it fresh instead.
  - Offered items are destroyed.
  - The currency is configurable, defaulting to emeralds.
  - No guild hall in 3.0. **Camps and repurposed towers are hubs with Turnover.** Their trial spawners are removed
    (13 spawner blocks across 7 templates).
- **M4:**
  - Travel to base: walk if loaded and close enough, otherwise a simulated delay.
  - Recruitment is by defeat or by payment, with the price based on favor.
  - "Set rendezvous point here." stores the player's exact position, and must be within 64 blocks of spawn.
  - Dismissed companions walk away, then simulate the rest of the walk and are gone.
  - Lost companions are restored from their snapshot.
  - Weapons a companion can't use are refused.

- **Round 3:**
  - **Faction relations:** never all three at war.
  - **Standing** is shown as a tier in the dialogue header.
  - **Retired worldgen:** `pit` is deprecated (no longer generates). The guild hall structure and dimension are off.
  - **Hubs:** 8 residents each, rotating every 3 days. The doc recommends a staggered half-swap.
  - **Prices:** at most ×2 when angry, about ×0.75 at best.
  - **Cross-dimension trips:** at most 2 days.
  - **Rumors:** precise at good Standing, 80% correct at neutral, 40% when angry. Gossip lets a player know they've
    been asked about. Told rumors are remembered per player, and only true ones count as told.

- **Round 4:**
  - **Hub spawning:** camp and tower `spawn_overrides` are removed.
  - **Hub rotation:** staggered, 4 of 8 residents per rotation.
  - **Stale rendezvous:** dropped when the spawn point moves out of range.
  - **Rumor precision:** PRECISE means a fine bearing and a tight band, not coordinates.
  - **Gossip** names the player who asked.
  - **Rumor subjects:** only players who have talked to an NPC can be the subject of a rumor.
